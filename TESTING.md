# Testing Strategy

How we prove each feature works. Requirement IDs refer to `REQUIREMENTS.md`; phase gates in `ROADMAP.md` require the sections below to pass.

## 1. Test levels and tools

| Level | Tool | Scope | When it runs |
|---|---|---|---|
| Static | `tsc --noEmit`, ESLint, Prettier, ruff | Types, lint, format | Every change |
| Unit | Vitest | Pure logic: Zod schemas, caption chunking, timecode utils, crypto, quota maths, recommendation rules, path resolution | Every change |
| Integration (app) | Vitest + temporary SQLite DB | Services, route handlers, job queue claim/lease/retry, result handlers | Every change |
| Unit/integration (worker) | pytest | Job modules with FFmpeg-generated fixtures; LLM/TTS/stock providers mocked | Every change to `media-worker/` |
| End-to-end | Playwright (Chromium) | Real browser against the running app + workers, mocked external APIs | End of each phase, before merging larger features |
| Manual | Checklist below | Visual quality, real YouTube channel, real models | End of each phase |

CI: not set up yet (the project has no remote repository). When one exists, a GitHub Actions workflow can run `npm ci && npm run check && npm run build`. Workflows that need FFmpeg, Ollama or YouTube stay local.

Isolation: Vitest creates a temporary migrated database, storage folder and test-only secrets (`tests/support/global-setup.ts`); Playwright starts its own app (port 3200) and media worker with `data/e2e.db`, `data/e2e-storage` and FFmpeg-generated samples in `data/e2e-media`, recreated on every run. None of them touch `data/app.db`, your storage or your `.env` secrets. E2E needs FFmpeg on PATH and `npm run worker:setup` done once; worker tests: `npm run worker:test`.

## 2. Test data and doubles

- **Media fixtures are generated, not committed:** a pytest/Vitest helper creates short clips with FFmpeg (`testsrc2` video + `sine` audio, 1080p/720p, 16:9 and 9:16, 5–30 s). One committed exception: a ≤ 300 KB speech sample (public-domain or self-recorded) for transcription tests.
- **Corrupt files:** a text file renamed to `.mp4`, a truncated MP4, a zero-byte file.
- **LLM:** a `FakeLLMProvider` returns fixed JSON (valid, invalid, oversized) to test parsing, retries and validation. Real-model quality is evaluated manually (§5).
- **YouTube/Google:** HTTP-level mocks (fixture JSON for `channels.list`, `videos.insert` resumable session, `reports.query`, error responses `quotaExceeded`, `invalid_grant`, `uploadLimitExceeded`). Automated tests never call real Google APIs.
- **Pexels/Pixabay:** recorded fixture responses; downloads served from a local test server.
- **Database:** each integration test file uses a fresh temporary SQLite file with migrations applied.

## 3. Feature acceptance tests and completion criteria

A feature is complete when every listed test passes **and** all its **M** requirements are covered.

## 4. Security tests (all phases, `SECURITY.md`)

- Every route under `/api` (except auth, health, internal) returns 401 without a session — enforced by an automated test that enumerates route files.
- Cross-user access: a second test user cannot read/modify another user's video, Short, job or media file (even though v1 has one owner, the code path is tested).
- Path traversal: `storage.resolve` rejects `../`, absolute paths, encoded traversal, and symlinks out of root.
- Origin check: POST from a foreign `Origin` is rejected.
- Headers: CSP, `X-Frame-Options`, `nosniff` present on pages and media responses.
- Secrets: `npm run check:secrets` scans the built client bundle for configured secret values (names appear legitimately in help text); log-redaction unit tests (Node and Python).
- No `.env`, database, storage, backup or credential files among the files Git tracks or would add — checked by `npm run check:secrets` (Phase 10).
